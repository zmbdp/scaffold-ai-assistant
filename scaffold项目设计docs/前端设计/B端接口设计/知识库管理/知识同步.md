# 知识同步

## 功能介绍

知识同步是把知识源路径下的文件「扫描 → 哈希比对 → 分块 → 向量化 → 写入 Milvus」的过程，是知识库从「配置」变成「可检索」的关键动作。B 端「知识库管理 → 知识同步」页面用于：

- 手动触发一次同步（可选择只同步某类知识源，或强制全量重建）；
- 通过返回的 `taskId` 轮询同步进度（当前正在同步的知识源、已处理文件数、成功/失败/跳过计数、最终统计结果）。

本接口为**异步**实现：admin-service 通过 Feign 调用 chat-service，chat-service 生成 `taskId` → 校验单任务约束 → 投递 RabbitMQ 消息后立即返回 `SyncTaskVO`（含 `taskId`）。真正的同步流程由 chat-service 的 `KnowledgeSyncConsumer` 异步消费执行，过程中实时把进度写入 Redis（key = `sync:progress:{taskId}`，TTL 24 小时），前端用 `taskId` 调用进度查询接口轮询展示进度条。

> 公共约定（网关地址、JWT 认证、`Result<T>` 结构、统一错误码、操作审计说明）见 `B端接口设计/总说明.md`，本文不再重复，仅说明本模块特有内容。

## 接口清单

| 序号 | 方法 | 路径 | 说明 | 操作审计 |
| --- | --- | --- | --- | --- |
| 1 | POST | `/admin/knowledge/sync` | 触发知识同步（异步，返回 taskId） | 是 |
| 2 | GET | `/admin/knowledge/sync/progress/{taskId}` | 查询同步任务进度（轮询） | 否（只读查询） |

> **单任务约束**：同时只允许一个同步任务执行。若已有任务在 RUNNING 状态，再次提交会返回 `status=SKIPPED` 及当前正在执行的任务ID，前端应使用该 `taskId` 轮询进度，无需重新触发。
>
> **进度历史**：只保留当前/最近一次任务进度，存储在 Redis（TTL 24 小时），不做历史记录表。任务完成或失败后进度仍保留 24 小时供查询，过期后查询返回 `null`。

## 1. 触发知识同步（异步）

### 1.1 接口信息

| 项 | 值 |
| --- | --- |
| 方法 | `POST` |
| 路径 | `/admin/knowledge/sync` |
| 认证 | 需要（`userFrom=sys`） |
| Content-Type | `application/json` |
| 操作审计 | 是：`@LogAction(value = "知识同步", module = "knowledge", recordParams = true)`（记录入参到 `operation_log` 表） |
| 同步方式 | **异步**（RabbitMQ），接口立即返回 `SyncTaskVO` |

### 1.2 请求参数（Body：SyncReqDTO）

| 字段 | 类型 | 必传 | 默认值 | 校验规则 | 含义 |
| --- | --- | --- | --- | --- | --- |
| `sourceType` | String | 否 | `all`（null 也视为全部） | 无校验注解 | 同步类型过滤：`all` / `doc` / `javadoc` / `config` / `code` |
| `force` | Boolean | 否 | `false` | 无校验注解 | 是否强制全量重新同步。`false`=增量（仅同步哈希变更的文件）；`true`=全量（跳过哈希检查，所有文件视为更新） |

> **`force` 判定**：源码中 `boolean force = dto != null && Boolean.TRUE.equals(dto.getForce())`，即仅当显式传 `true` 才全量，传 `false` / `null` / 不传均为增量。

### 1.3 请求示例

**增量同步（最常用）**：

```http
POST /admin/knowledge/sync
Authorization: Bearer {accessToken}
Content-Type: application/json

{
  "sourceType": "all",
  "force": false
}
```

**强制全量重新同步**（修改了 chunkSize/chunkOverlap 或怀疑向量丢失时使用）：

```json
{
  "sourceType": "all",
  "force": true
}
```

**仅同步代码类知识源**：

```json
{
  "sourceType": "code",
  "force": false
}
```

### 1.4 响应结构

`Result<SyncTaskVO>`，`data` 为同步任务提交结果，**不是同步统计结果**。

#### SyncTaskVO 字段定义

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `taskId` | String | 同步任务ID（UUID 去横线）。`status=RUNNING` 时为本次新生成的 taskId；`status=SKIPPED` 时为当前正在执行的任务ID |
| `status` | String | 提交状态：`RUNNING`（新任务已提交）/ `SKIPPED`（被跳过，已有任务在执行） |
| `message` | String | 提示信息，可直接展示给用户 |

> **关键**：`code=200000` 仅表示 MQ 消息已成功投递，不代表同步已完成或成功。同步流程在 chat-service 后台异步执行，前端需用 `taskId` 调用 `GET /admin/knowledge/sync/progress/{taskId}` 轮询进度。

### 1.5 响应示例

**新任务已提交（status=RUNNING）**：

```json
{
  "code": 200000,
  "errMsg": "操作成功",
  "data": {
    "taskId": "a1b2c3d4e5f6789012345678abcdef00",
    "status": "RUNNING",
    "message": "同步任务已提交，请使用 taskId 轮询进度"
  }
}
```

**已有任务在执行，本次被跳过（status=SKIPPED）**：

```json
{
  "code": 200000,
  "errMsg": "操作成功",
  "data": {
    "taskId": "a1b2c3d4e5f6789012345678abcdef00",
    "status": "SKIPPED",
    "message": "已有同步任务在执行，可使用返回的 taskId 查询进度"
  }
}
```

> **SKIPPED 处理建议**：前端收到 `status=SKIPPED` 时，应直接用返回的 `taskId` 切换到轮询进度，提示用户「已有同步任务在执行」，不要提示「提交失败」。

### 1.6 提交端内部流程（chat-service `KnowledgeServiceImpl.sync`）

1. 读取 Redis key `sync:current-task`（指向当前执行中的 taskId，TTL 24h）。
2. 若 key 存在，查询其指向任务的进度：若状态为 `RUNNING`，返回 `status=SKIPPED` 及当前 taskId，本次不投递 MQ 消息。
3. 否则生成新 taskId（UUID 去横线），封装 `KnowledgeSyncMessage`（含 taskId、sourceType、force），投递到 Direct 交换机 `knowledge.sync.exchange`（路由键 `knowledge.sync`）。
4. 返回 `status=RUNNING` 及新 taskId。

> **单任务约束的两道防线**：
> - **提交端去重（best-effort）**：通过 `sync:current-task` 判断，极端场景下（提交后、消费前的短暂窗口）可能投递多条 MQ 消息。
> - **消费端全局锁（强保证）**：`KnowledgeLoaderServiceImpl.syncKnowledge` 内部通过 Redisson 全局锁 `sync:global-lock` 保证同时只有一个同步任务执行。后到的任务获取锁失败时，向 Redis 写入 `status=SKIPPED` 的进度并返回 null，不会产生数据不一致。

## 2. 查询同步任务进度（轮询）

### 2.1 接口信息

| 项 | 值 |
| --- | --- |
| 方法 | `GET` |
| 路径 | `/admin/knowledge/sync/progress/{taskId}` |
| 认证 | 需要（`userFrom=sys`） |
| 操作审计 | 否（只读查询，无 `@LogAction`） |
| 数据来源 | Redis（key = `sync:progress:{taskId}`，TTL 24 小时） |

### 2.2 路径参数

| 参数 | 类型 | 必传 | 含义 |
| --- | --- | --- | --- |
| `taskId` | String | 是 | 同步任务ID（由 `POST /admin/knowledge/sync` 返回） |

### 2.3 请求示例

```http
GET /admin/knowledge/sync/progress/a1b2c3d4e5f6789012345678abcdef00
Authorization: Bearer {accessToken}
```

### 2.4 响应结构

`Result<SyncProgressVO>`，`data` 为同步进度数据。`taskId` 不存在或已过期（超过 24 小时）时 `data` 为 `null`。

#### SyncProgressVO 字段定义

| 字段 | 类型 | 含义 | 何时填充 |
| --- | --- | --- | --- |
| `taskId` | String | 同步任务ID | 全程 |
| `status` | String | 任务状态：`RUNNING` / `COMPLETE` / `FAILED` / `SKIPPED` | 全程 |
| `startTime` | Long | 同步开始时间（毫秒时间戳） | 全程 |
| `duration` | Long | 同步耗时（毫秒） | 完成/失败/跳过时填充 |
| `totalSources` | Integer | 知识源总数 | 预扫描后填充 |
| `currentSourceIndex` | Integer | 当前正在同步的知识源序号（从 1 开始） | 每个知识源开始时更新 |
| `currentSourceName` | String | 当前正在同步的知识源名称 | 每个知识源开始时更新 |
| `totalFiles` | Integer | 待同步文件总数（预扫描阶段统计） | 预扫描后填充 |
| `processedFiles` | Integer | 已处理文件数（成功 + 失败 + 跳过） | 每个文件处理完递增 |
| `successFiles` | Integer | 成功处理的文件数（新增 + 更新） | 每个文件处理完递增 |
| `failedFiles` | Integer | 处理失败的文件数 | 失败时递增 |
| `skippedFiles` | Integer | 跳过的文件数（哈希未变，仅增量模式有值） | 跳过时递增 |
| `lastFileName` | String | 最近处理的文件名 | 每个文件处理完更新 |
| `lastError` | String | 最近的错误信息 | 失败时填充 |
| `finalResult` | SyncResultVO | 最终统计结果 | `status=COMPLETE` 时填充 |

#### status 状态流转

| 值 | 含义 | 触发时机 |
| --- | --- | --- |
| `RUNNING` | 同步进行中 | 任务开始，`processedFiles` 逐步递增 |
| `COMPLETE` | 同步完成 | 所有知识源处理完毕，`finalResult` 填充最终统计 |
| `FAILED` | 同步异常终止 | 同步流程抛出未捕获异常，`lastError` 填充错误信息 |
| `SKIPPED` | 被跳过 | 消费端获取全局锁失败，已有任务在执行 |

#### finalResult（SyncResultVO）字段定义

> `finalResult` 仅在 `status=COMPLETE` 时填充，是同步完成后的最终统计。它嵌套在 `SyncProgressVO` 内返回给前端，不再单独以接口形式提供。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `totalDocuments` | Integer | 扫描到的文档总数 |
| `updatedDocuments` | Integer | 新增 + 更新的文档数 |
| `deletedDocuments` | Integer | 删除的文档数 |
| `skippedDocuments` | Integer | 跳过的文档数（哈希未变，仅增量模式有值） |
| `failedDocuments` | Integer | 处理失败的文档数 |
| `duration` | Long | 同步耗时（毫秒） |

## 3. 同步内部流程（chat-service 异步执行）

admin-service 通过 Feign 调用 chat-service 的 `KnowledgeApi.sync`，chat-service 生成 taskId 后投递 MQ 消息。`KnowledgeSyncConsumer` 消费消息后调用 `KnowledgeLoaderServiceImpl.syncKnowledge(sourceType, force, taskId)`，执行以下流程：

1. 查询所有 `enabled=1` 的知识源（`sourceType` 非空且非 `all` 时按类型过滤）。
2. **获取全局锁** `sync:global-lock`（Redisson，单任务约束）：
   - 获取失败：向 Redis 写入 `status=SKIPPED` 的进度（`lastError="已有同步任务在执行"`），返回 null，流程结束。
   - 获取成功：继续后续步骤。
3. 预扫描所有知识源路径，统计待同步文件总数（仅遍历目录不读内容，速度较快）。
4. 初始化进度对象 `SyncProgressVO`（status=RUNNING）写入 Redis，同时写入 `sync:current-task`（value=taskId，TTL 24h）供提交端去重。
5. 遍历每个知识源，更新进度（`currentSourceIndex` / `currentSourceName`）：
   - 按知识源粒度加 Redisson 分布式锁（`knowledge:sync:{knowledgeSourceId}`，租约 30 分钟）。
   - 遍历知识源路径，收集当前所有文件（path 可指向单文件或目录，目录时递归扫描匹配扩展名的文件）。
   - 从 `sys_ai_document` 查询该知识源已有文档（不含 DELETED）。
   - 对比文件路径，识别「新增 / 更新 / 删除」三种状态。
   - **新增文件**：读内容 → 算 SHA-256 哈希 → 分块 → 插 MySQL → 写 Milvus。
   - **更新文件**：读内容 → 算哈希 → MySQL `version+1` → 删旧 Milvus 分块 → 重新分块 → 写新 Milvus 分块。
   - **删除文件**：删 Milvus 分块 → MySQL `status=DELETED`（软删除）。
   - **`force=true` 时**：跳过哈希检查，所有已存在文件均视为「更新」重新分块写入。
   - **增量跳过条件**（`force=false` 时，三者同时满足才跳过）：哈希相同 + `chunk_count > 0` + 哈希非空字符串。任一不满足都重新同步（覆盖上次失败回滚的场景）。
   - 每个文件处理完后更新进度（`processedFiles` / `successFiles` / `failedFiles` / `skippedFiles` / `lastFileName`）并写入 Redis。
   - 更新知识源 `lastSyncDate` 与 `updateDate`。
   - 释放知识源级分布式锁。
6. 全部完成：写入 `status=COMPLETE` 进度，填充 `duration` 和 `finalResult`（SyncResultVO 统计）。
7. 异常：写入 `status=FAILED` 进度，填充 `duration` 和 `lastError`，重新抛出异常触发 MQ 重试。
8. `finally` 释放全局锁。

> **失败处理**：单文件处理失败计入 `failedFiles`/`failedDocuments`，不影响其他文件继续同步。知识源级异常会计入该知识源失败数并继续下一个知识源。整体流程异常会写入 FAILED 进度并抛出异常，MQ 会自动重试（默认 3 次）。

## 错误码说明

> **注意**：本模块业务逻辑主要在 chat-service 执行，B 端接口经 admin-service Feign 透传。chat-service 的业务错误码会被抹平为 `500000`（仅透传 errMsg），前端应以 `code !== 200000` 判断失败，不要硬编码特定 code。

| 场景 | 前端实际收到 | errMsg 示例 |
| --- | --- | --- |
| 同步任务提交成功 | `200000` | `操作成功`（`data` 为 SyncTaskVO） |
| 进度查询成功 | `200000` | `操作成功`（`data` 为 SyncProgressVO 或 null） |
| MQ 投递失败（RabbitMQ 异常） | `500000` | `触发知识同步失败：xxx` |
| Feign 调用 chat-service 失败 | `500000` | `触发知识同步失败` / `查询同步进度失败` |
| token 缺失/无效/越权 | `401000` / `401001` / `401003` / `401004`（HTTP 401） | 见总说明 |

> **异步同步内部失败不回传错误码**：若 chat-service 消费端同步执行中部分文件失败（如 Embedding 超时、Milvus 写入异常），前端**不会**收到错误码，需通过进度查询接口的 `failedFiles` / `lastError` 字段观察。整体异常终止时进度状态为 `FAILED`，`lastError` 填充错误信息。

## 枚举值

### 同步类型 `sourceType`

| 值 | 含义 |
| --- | --- |
| `all` | 全部知识源（传 null 也等同 all） |
| `doc` | 仅 Markdown 文档知识源 |
| `javadoc` | 仅 JavaDoc HTML 知识源 |
| `config` | 仅配置文件知识源 |
| `code` | 仅 Java 源码知识源 |

> `sourceType` 实际是按 `sys_ai_knowledge_source.type` 字段过滤知识源（`sourceType` 非空且不等于 `all` 时 `WHERE type = ?`）。传任意其他字符串会因无匹配类型的知识源而空跑（同步 0 个知识源，进度直接置为 COMPLETE）。

### `force` 参数语义

| 值 | 含义 | 适用场景 |
| --- | --- | --- |
| `false`（默认） | 增量同步：哈希未变且 `chunk_count>0` 且哈希非空的文件跳过 | 日常同步，文件未改不动 |
| `true` | 全量同步：跳过哈希检查，所有已存在文件重新分块写入向量 | 修改了 chunkSize/chunkOverlap、怀疑向量丢失、Embedding 模型变更后重建向量 |

### SyncTaskVO.status（提交状态）

| 值 | 含义 | 前端处理 |
| --- | --- | --- |
| `RUNNING` | 新任务已提交，同步流程即将开始或已在执行 | 用返回的 taskId 开始轮询进度 |
| `SKIPPED` | 已有同步任务在执行，本次提交被跳过 | 用返回的 taskId（当前正在执行的任务）轮询进度，提示用户「已有任务在执行」 |

### SyncProgressVO.status（任务状态）

| 值 | 含义 | 前端处理 |
| --- | --- | --- |
| `RUNNING` | 同步进行中 | 继续轮询，展示进度条 |
| `COMPLETE` | 同步完成 | 停止轮询，展示 `finalResult` 统计结果 |
| `FAILED` | 同步异常终止 | 停止轮询，展示 `lastError` 错误信息 |
| `SKIPPED` | 消费端获取全局锁失败，被跳过 | 停止轮询，提示「已有任务在执行」 |

## 前端注意事项

1. **接口是异步的，返回不等于完成**：`POST /sync` 返回 `code=200000` 只表示 MQ 消息已投递，同步在后台异步执行（可能数分钟）。收到 `status=RUNNING` 后应立即开始轮询进度，不要提示「同步完成」。
2. **轮询推荐做法**：
   - 触发同步后拿到 `taskId`，每 2-5 秒调用一次 `GET /sync/progress/{taskId}`。
   - `status=RUNNING` 时更新进度条（`processedFiles / totalFiles`）、当前知识源名称、已处理/成功/失败/跳过计数。
   - `status=COMPLETE` 时停止轮询，展示 `finalResult` 最终统计。
   - `status=FAILED` 时停止轮询，展示 `lastError`。
   - `status=SKIPPED` 时停止轮询，提示「已有同步任务在执行」。
   - `data=null` 时表示 taskId 不存在或已过期（超过 24 小时），停止轮询并提示「任务进度已过期」。
3. **单任务约束的处理**：重复提交同步不会报错，会返回 `status=SKIPPED` 及当前正在执行的任务ID。前端应直接切换到该 taskId 轮询进度，不要提示「提交失败」。建议触发按钮在轮询期间置灰防抖，避免高频重复点击。
4. **`force=true` 全量同步耗时较长**：会重新 Embedding 所有文件并重建向量，文件多时可能数分钟到数十分钟。前端应明确告知用户「全量重建耗时较长」，并建议在低峰期执行。
5. **`force=true` 会短暂导致向量缺失**：更新流程中「先删旧向量再写新向量」，若此期间发生 RAG 检索可能召回不全。非必要不用 force。
6. **修改分块参数后必须 force 同步**：知识源的 `chunkSize` / `chunkOverlap` 变更后，旧向量是按旧参数切的，增量同步（`force=false`）因哈希未变会跳过，导致向量与配置不一致。此时必须用 `force=true` 重建。
7. **进度数据 24 小时过期**：Redis 中进度数据 TTL 为 24 小时，过期后查询返回 `null`。不做历史记录表，如需长期保留同步结果请前端自行记录。
8. **定时同步任务**：除手动触发外，XXL-JOB 调度中心默认每日凌晨 2:00 执行一次增量同步（`knowledgeSyncJob`，参数 `false`）。定时任务不生成 taskId，不写入进度数据，前端无需关心，了解即可。
9. **`sourceType` 传非法值**：传 `all` / `doc` / `javadoc` / `config` / `code` 之外的值（如 `abc`）不会报错，但会因无匹配类型的知识源而空跑（同步 0 个文件），进度直接置为 `COMPLETE`。前端应限制选项为合法枚举。
